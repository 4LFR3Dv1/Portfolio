# R0.7 — Route + Language Identity

Status: **MATERIALIZED / AWAITING WITNESS**

Portfolio baseline: `main@8e13bf9f462abdb690ef4486d9b933e2a3405bd2`

Precondition: `R0_6_COMPLETE=true`.

R0.7 freezes how public locators and language realizations identify already-defined Records without becoming ontology themselves.

It adds **zero RecordKinds**.

Instead, it materializes two identity-registry entry types:

```text
identity.route-binding
identity.language-binding
```

These are not Records. They are registry entries that extend the R0.2 locator/representation identity laws.

The governing separation is:

```text
RecordId
  = durable logical identity

RevisionId
  = exact accepted historical state

RouteBinding
  = public locator -> logical Record

LanguageBinding
  = language realization -> exact Record revision

URL / slug / locale / translated text
  != Record identity
```

## 1. R0.2 locator law becomes executable

R0.2 already froze:

```text
locator -> RecordId
locator != RecordId
```

and forbids silently reassigning a historical public locator to another Record.

R0.7 now defines the concrete public Record-route grammar and route registry behavior.

A route binding is:

```ts
{
  schemaVersion: 'identity.route-binding/v0'
  path: string
  targetRef: RecordRef
  admittedAgainst: PinnedRecordRef
  language: 'pt-BR' | 'en'
  role: 'canonical' | 'alias'
}
```

`targetRef` is the durable logical target.

`admittedAgainst` records the exact target revision that existed when the path was admitted. It is historical provenance for the binding; it does not make the route revision-bound.

Therefore:

```text
Record revision N
  -> route admitted

Record revision N+1
  -> same route still identifies same RecordId
```

The route does not need to be re-minted merely because the Record advances.

## 2. Public Record-route grammar

R0.7 freezes the Record locator grammar:

```text
/<locale>/<namespace>/<slug>
```

Initial admitted locale segments are:

```text
pt-BR -> pt-br
en    -> en
```

Initial Record namespaces are:

```text
systems
questions
investigations
experiments
essays
research
notes
architecture
```

Examples:

```text
/pt-br/systems/genesis
/en/systems/genesis

/pt-br/essays/identity-as-lineage
/en/research/evidence-and-authority

/pt-br/architecture/governed-execution
```

Canonical Record paths are lowercase ASCII and contain exactly three segments after the leading slash.

Slug grammar is:

```text
[a-z0-9]+(?:-[a-z0-9]+)*
```

with maximum length 80.

Canonical Record paths do not contain:

```text
query string
fragment
percent-encoded alternate spelling
uppercase characters
trailing slash
```

Those may exist at an HTTP layer later, but they are not distinct canonical Record locator identities.

## 3. Namespace compatibility

The route namespace communicates public information architecture, not ontology identity, but R0.7 prevents namespace/type contradiction.

Frozen compatibility:

```text
systems
  -> knowledge.system

questions
  -> knowledge.question

investigations
  -> knowledge.investigation

experiments
  -> knowledge.experiment

essays
  -> representation.publication / essay

research
  -> representation.publication /
       research-note | experiment-report | technical-paper

notes
  -> representation.publication / system-note

architecture
  -> representation.architecture
```

`knowledge.claim`, Evidence and governance Records have no direct canonical Record-route namespace in R0.7.

That does not make them private or inaccessible. Exposure is still governed by R0.6 and later projections may cite or embed them. R0.7 merely does not grant them standalone canonical page identity.

## 4. Canonical routes and aliases

For every registered pair:

```text
RecordId + language
```

there is exactly one current canonical path.

Any additional registered path for that pair is an alias.

Example:

```text
/pt-br/systems/genesis       canonical
/pt-br/work/genesis          legacy alias in a future R0.8 mapping
```

R0.7 does not create the legacy alias yet; R0.8 owns migration.

When a canonical route moves:

```text
old canonical
    ↓
alias to same RecordId + same language

new canonical
    ↓
canonical
```

The old public locator is never freed for another Record.

## 5. Historical path reservation

A previously admitted path may not disappear from identity history and may not be rebound to another Record.

Registry evolution therefore preserves:

```text
path
target RecordId
language
admittedAgainst
```

The route role may change between `canonical` and `alias`, but the historical locator target and language do not.

This allows a canonical route to move while keeping the old path durable.

## 6. Canonical URL

The R0.7 Record origin is:

```text
https://renan.snelabs.space
```

Canonical URL is:

```text
origin + canonical Record path
```

For example:

```text
https://renan.snelabs.space/pt-br/systems/genesis
```

Query strings and fragments are never part of canonical Record identity.

Collection/service routes such as home, archive, search, tags or RSS are not Record locators and are not governed by the Record route-binding grammar in this cut.

## 7. Language realization is not a new Record

R0.2 already froze that changing language representation does not by itself mint another logical Record.

R0.7 makes that operational with:

```ts
{
  schemaVersion: 'identity.language-binding/v0'
  targetRef: RecordRef
  basisRef: PinnedRecordRef
  language: 'pt-BR' | 'en'
  role: 'canonical' | 'translation'
  translatedFrom: 'pt-BR' | 'en' | null
  realizationDigest: PayloadDigest
}
```

A language binding is revision-bound.

It answers:

```text
for this exact Record revision,
which language realization exists?
```

It does not answer:

```text
what Record is this?
```

That remains `RecordId`.

## 8. Canonical language realization

For each exact Record revision that has language bindings, exactly one realization is canonical.

For a canonical language binding:

```text
role = canonical
translatedFrom = null
realizationDigest = exact target revision PayloadDigest
```

The canonical language therefore identifies the language of the canonical semantic payload bytes already admitted by the owning R0.3/R0.4/R0.5 schema.

It does not create another payload authority.

## 9. Translation realization

A translation:

```text
role = translation
```

must:

```text
bind the same exact target revision
use a different language
identify the canonical source language
carry its own immutable realization digest
```

A translation does not revise the underlying Record.

It does not create new:

```text
Claims
Evidence bindings
maturity
disclosure
System identity
Publication identity
```

If translated prose would materially introduce different machine-addressable meaning, that change belongs in the canonical semantic graph rather than being smuggled through localization.

## 10. Translation is optional

R0.7 does not require every Record to be bilingual.

These are valid:

```text
PT-BR only
EN only
PT-BR canonical + EN translation
EN canonical + PT-BR translation
```

Missing translation means only:

```text
that language realization is unavailable for that exact revision
```

It does not mean:

```text
private
withheld
false
unsupported
nonexistent
```

## 11. No implicit language fallback

Language resolution fails closed.

If:

```text
/en/... requested
```

but the current exact Record head has no admitted `en` language binding, the result is:

```text
language-unavailable
```

not:

```text
serve PT-BR anyway
```

Browser `Accept-Language`, local storage, previous UI preference or current application state may later help navigation, but they do not alter canonical URL identity.

## 12. New Record revision invalidates stale language availability

Route identity is logical and survives Record revisions.

Language availability is exact-revision-bound and does not.

Therefore:

```text
Record head = revision N
PT-BR language binding for N
EN language binding for N

Record advances to revision N+1

route bindings remain valid
PT-BR availability for current head = unavailable
EN availability for current head    = unavailable

until bindings for N+1 are admitted
```

This prevents an old translation from silently being presented as a translation of new content.

## 13. Current route resolution

R0.7 identity resolution is:

```text
path
  -> RouteBinding
      -> logical RecordId
          -> current admissible head
              -> exact LanguageBinding for requested language
                  -> current canonical route for RecordId + language
```

Possible identity outcomes are:

```text
unresolved
head-unavailable
language-unavailable
conflict
resolved
```

An alias resolves to the same Record and language but indicates redirection to the current canonical path.

## 14. Unknown route is not landing identity

The current legacy SPA falls back from unknown paths to the landing view.

R0.7 explicitly rejects that behavior as a **Record identity rule**.

```text
unbound path
  != home Record
  != landing Record
  != nearest route
```

Its identity outcome is:

```text
unresolved
```

R0.7 does not yet modify the runtime router. R0.8/R1 will reconcile runtime behavior against this frozen contract.

## 15. R0.6 remains exposure authority

A valid route plus a current language realization does not authorize publication.

Current public projection still requires R0.6 eligibility:

```text
target lifecycle eligible
AND
current disclosure classified
AND
visibility.record = public
AND
disclosure != withheld
AND
valid route identity
AND
current requested language realization
```

R0.7 never upgrades a private, withdrawn, tombstoned or disclosure-conflicted Record into a public one.

## 16. Route identity and language identity remain external

R0.7 adds zero new RecordKinds because:

```text
route
language tag
translation realization
slug
canonical URL
alias
```

are address/representation properties, not new knowledge, evidence, representation or governance entities.

They belong to the identity registry first frozen by R0.2.

## 17. Legacy route and language migration

R0.7 defines the target contract but does not migrate the current Portfolio.

R0.8 must reconcile the R0.0 frozen world, including:

```text
/
/architecture
/work/:projectId
current same-path EN/PT client state
manual sitemap
current canonical root metadata
```

against the new route/language registry.

Existing public URLs must not be silently broken or reassigned.

## 18. Canonical registry entry bytes

Both registry entry types use canonical JSON:

```text
UTF-8
object keys lexicographically sorted
no insignificant whitespace
terminal LF
exact field sets
SHA-256 digest
```

The entry digest is a witness for the registry entry bytes. It is not a RecordId or RevisionId.
