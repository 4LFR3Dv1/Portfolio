# R1.3 — Route Runtime

Status: **COMPLETE / CI WITNESSED**

Baseline: `main@daee2f130295aca2c4a27edb760a9734d5f030ba`

Preconditions:

```text
R0_EFFECTIVE_COMPLETE=true
R1_1_COMPLETE=true
R1_2_COMPLETE=true
```

R1.3 materializes the executable Record-route registry and path resolver without inventing new public addresses from Record existence.

The central separation is:

```text
Record exists
    !=
route exists
    !=
language realization exists
    !=
public projection exists
```

## 1. Route admission is explicit

R1.3 does not implement:

```text
RecordId -> derive slug -> publish route
```

Every route binding is explicitly listed in `route-runtime.v0.json` and must target a Record that was already born in the sealed R1.1 registry.

The initial route batch is deliberately conservative. It enacts only the still-valid R0.8 canonical System-route plans whose targets actually exist after R1.1 and R0-A1 reconciliation.

## 2. Initial admitted route set

The effective R0.8/R0-A1 migration state yields five born System targets with previously frozen EN/PT-BR canonical route plans:

```text
VIRA
XS Wallet / Domini
Transactional Support Bot
SNE-OS
Foundry Pay
```

Each receives the two already-planned canonical path identities:

```text
/en/systems/<slug>
/pt-br/systems/<slug>
```

Therefore R1.3 starts with:

```text
born System Records             28
routed System Records             5
born Systems without route       23
canonical route bindings         10
alias route bindings              0
```

The remaining 23 born Systems do not receive routes by inference. Their future public addresses require a later explicit route-registry evolution.

## 3. Admission basis is the frozen Birth revision

A RouteBinding remains a logical locator:

```text
path -> RecordId
```

but R0.7 also requires historical admission provenance through `admittedAgainst`.

R1.3 derives that exact pinned admission basis from the immutable R1.1 generation-zero Birth materialization.

```text
route target       logical RecordId
admittedAgainst    exact R1.1 Birth RevisionId
```

This does not revision-pin the route itself.

If the Record later advances:

```text
route still identifies RecordId
current route resolution follows current admissible head
admittedAgainst remains historical Birth provenance
```

## 4. Agentic route plans remain cancelled

R0-A1 retired the never-born broad `Agentic Systems & Foundry` reservation and cancelled its never-enacted planned canonical paths:

```text
/en/systems/agentic-systems
/pt-br/systems/agentic-systems
```

R1.3 records those paths only as cancelled plans. They are not RouteBindings and are not available for runtime resolution.

The durable legacy `/work/agentic-systems` representation remains an R1.8 compatibility concern and is not rebound to Foundry, Factory or AgentHub.

## 5. Unborn representation routes remain unadmitted

R0.8 also planned routes for three Publications and five Architecture representations.

Those RecordIds remain held reservations after R1.1. A reservation is not a born Record.

R1.3 therefore creates zero routes for those eight identities.

Route existence cannot manufacture Record existence.

## 6. Route runtime is route-only

R0.7 ultimately resolves route and language together, but R1.3 intentionally stops before language realization.

The route-only resolver answers:

```text
is this path bound?
which logical Record does it identify?
what is that Record's current head?
what language identity does the route request?
what is the current canonical path for that Record/language pair?
is this binding canonical or alias?
```

It does **not** answer:

```text
does that exact head currently have an admitted language realization?
```

That is R1.4.

Therefore a PT-BR route may resolve at the route layer while still becoming `language-unavailable` once R1.4 language authority is applied.

## 7. Route-only outcomes

R1.3 exposes bounded route-runtime outcomes:

```text
unresolved
registry-conflict
head-unavailable
conflict
resolved
```

`unresolved` is preserved as itself. It does not mean home.

`registry-conflict` means the route registry itself failed validation and no path is trusted until the contradiction is repaired.

## 8. Canonical identity and alias semantics

The initial R1.3 batch has no aliases.

The runtime nevertheless implements canonical/alias semantics defined by R0.7 so future route evolution can preserve historical paths.

For one `RecordId + language` pair there must be exactly one canonical path. An alias resolves to the same current Record head but carries redirect intent toward the canonical path.

R1.3 does not choose an HTTP redirect status yet.

## 9. Historical path reassignment remains forbidden

Route registry evolution is validated against R0.7.

A path that has been admitted cannot later identify another Record merely because the newer destination seems more relevant.

```text
old path -> Record A

future evolution:
old path -> Record B

REJECT
```

Canonical movement is represented by preserving the old binding as an alias to the same logical Record and adding another canonical path.

## 10. Legacy compatibility is not RouteBinding admission

The legacy paths:

```text
/
/architecture
/work/:projectId
```

are not silently converted into R0.7 Record routes here.

R0.8 already established that the `/work/...` paths historically multiplexed language through client state and therefore cannot become ordinary language-specific R0.7 aliases without an explicit compatibility layer.

R1.8 owns that layer.

At R1.3:

```text
/work/vira -> unresolved in Record-route runtime
/          -> unresolved in Record-route runtime
```

This does not remove the currently deployed legacy surface because no framework cutover occurs.

## 11. No language fallback

Route bindings carry the language identity frozen by R0.7, but R1.3 materializes no `identity.language-binding` entries.

It also never maps:

```text
requested PT-BR -> serve EN
requested EN    -> serve PT-BR
```

Language realization and its fail-closed availability are R1.4 concerns.

## 12. No exposure authority

A valid route still does not imply publication.

R1.3 creates no disclosure Records and changes no R1.2 public projection decision.

The new editorial substrate therefore remains at:

```text
current public projections    0
```

until current disclosure and language authority are explicitly admitted.
