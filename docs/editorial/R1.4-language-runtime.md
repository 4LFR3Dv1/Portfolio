# R1.4 — Language Runtime

Status: **MATERIALIZED / AWAITING CI WITNESS**

Baseline: `main@2a0d93abbdf66e175175031d6ef2c1158e02a302`

Preconditions:

```text
R0_EFFECTIVE_COMPLETE=true
R1_1_COMPLETE=true
R1_2_COMPLETE=true
R1_3_COMPLETE=true
```

R1.4 materializes exact-revision language realizations and composes them with the R1.3 Route Runtime without allowing a route, locale segment or browser preference to manufacture content.

The central separation is:

```text
route exists
    !=
language realization exists
```

In particular:

```text
/pt-br/systems/vira exists
        ↓
DOES NOT imply
        ↓
PT-BR realization exists
```

A requested language is available only when an admitted `identity.language-binding` exists for the exact current Record revision.

## 1. Canonical language is exact payload identity

R1.1 admitted 28 generation-zero `knowledge.system` Records with canonical semantic payload bytes.

R1.4 explicitly admits those exact bytes as the canonical `en` realization for each of the 28 born System revisions.

It does not copy or reinterpret the canonical payload. For every canonical language binding:

```text
basisRef.revisionId      = exact R1.1 Birth RevisionId
language                 = en
role                     = canonical
translatedFrom           = null
realizationDigest        = exact Record payloadDigest
```

The canonical realization therefore has no second payload authority.

## 2. Translation is a separate realization, not a Record revision

A PT-BR realization does not mint a new Record and does not revise the underlying System.

The initial R1.4 PT-BR admissions exist only for born Systems whose effective R0.8 migration plan explicitly carried `pt-BR` translation intent:

```text
VIRA
XS Wallet / Domini
Transactional Support Bot
SNE-OS
Foundry Pay
```

The retired pre-Birth Agentic target is excluded because no such Record exists after R0-A1.

R1.4 therefore admits:

```text
28 canonical EN realizations
 5 explicit PT-BR translations
33 language bindings total
```

Translation inference is forbidden.

## 3. Translation bytes are independently digest-bound

The current R1.1 System Birth payload intentionally contains only:

```text
name
admission-safe summary
thesis = null
```

For the five explicit PT-BR translations, R1.4 preserves the canonical System name and thesis while translating only the admission-safe summary.

Each translated `knowledge.system/v0` realization is canonicalized under the existing R0.3 payload profile and receives its own immutable `PayloadDigest`.

Therefore:

```text
canonical EN realizationDigest = Record payloadDigest
PT-BR translationDigest        = digest(PT-BR realization bytes)
```

Neither digest becomes a new `RecordId` or `RevisionId`.

## 4. Exact revision binding is mandatory

Every language binding uses:

```text
targetRef = logical RecordId
basisRef  = exact PinnedRecordRef
```

Language availability is evaluated against the current exact head.

If a Record advances from revision N to revision N+1:

```text
route binding survives logically
language realization for N becomes stale for current-head resolution
```

Until a language binding for N+1 is explicitly admitted, the result is:

```text
language-unavailable
```

for that requested language.

No stale EN or PT-BR realization is inherited.

## 5. Missing translation remains missing

R1.4 does not use:

```text
Accept-Language
localStorage
previous client preference
route locale as evidence of content
canonical language as automatic fallback
```

to repair missing content.

If a PT-BR route exists but the exact PT-BR realization is absent, the route/language composition returns:

```text
language-unavailable
```

It does not serve EN under a PT-BR canonical URL.

## 6. Route Runtime + Language Runtime composition

R1.4 composes the already-validated registries through the R0.7 resolution semantics:

```text
path
  ↓
R1.3 Route Runtime
  ↓ logical RecordId
current exact Record head
  ↓
R1.4 Language Runtime
  ↓ exact language binding for that head
resolved | language-unavailable | conflict
```

Registry-level route or language conflict is a build failure. Request-level absence remains an explicit identity outcome.

For the current admitted state all ten R1.3 canonical routes resolve because each of those five Systems has exact EN and PT-BR realization for its current generation-zero head.

## 7. Language does not authorize publication

R1.4 admits language identity only.

It does not admit:

```text
governance.disclosure
governance.maturity
public projection authority
document rendering
legacy language negotiation
```

Therefore the new editorial substrate still has zero public Record projections even though ten routed language pairs can now resolve.

A resolved language identity plus route is still omitted by R1.2 when disclosure is unclassified.

## 8. No document runtime yet

A language realization proves exact semantic bytes for one Record revision and language. It is not yet an editorial page.

R1.5 owns the later transformation:

```text
resolved public projection
        +
exact language realization
        ↓
Editorial Document DTO
```

R1.4 does not install Astro, render pages, create UI, generate RSS or enact framework cutover.
