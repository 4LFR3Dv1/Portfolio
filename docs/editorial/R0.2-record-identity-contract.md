# R0.2 — Record Identity Contract

Status: **NORMATIVE / IN PROGRESS**

Portfolio baseline: `main@f5d17bc3d76f55c1ca4e95cc0508e50aa079aa84`

Precondition: `R0_2_PRE_COMPLETE=true`.

R0.2 defines what it means for one editorial Record to remain the same Record while its mutable state, revision, representation, storage realization, route or interpretation changes. This cut introduces no System, Question, Investigation, Experiment, Claim, Evidence, Architecture or Publication kinds. R0.3 will populate the first ontology registry after this identity substrate is frozen.

## 1. Identity layers

R0.2 separates five classes of identity that MUST NOT be collapsed:

```text
RecordId
  stable logical identity of one Record

RecordKind
  constitutive ontological class fixed at birth

RevisionId
  immutable identity of one exact accepted revision

PayloadDigest
  immutable digest of the revision payload supplied by the kind-specific layer

RecordLocator
  route, slug, filename or external handle that resolves to a Record
```

Consequently:

```text
RecordId != RevisionId
RecordId != PayloadDigest
RecordId != RecordLocator
RevisionId != PayloadDigest
RecordLocator != ontological identity
```

## 2. RecordId

The canonical textual form is:

```text
rec_<32 lowercase hexadecimal characters>
```

Example:

```text
rec_9f2a2c7e4d6b4f7398b4f6f9e2c61a03
```

`RecordId` is opaque. It MUST NOT encode or derive from title, slug, language, route, kind, author, timestamp, repository path, content digest, framework, deployment target or current state.

A RecordId is provisioned before birth and admitted only after a registry uniqueness check. Once admitted, it is globally reserved forever, including after withdrawal, archival or tombstone.

## 3. RecordKind

`RecordKind` is a namespaced lowercase token:

```text
segment.segment[-segment]...
```

The identity contract validates only the grammar. R0.3 owns the first normative kind registry.

Kind is constitutive:

```text
birth.kind == every_successor.kind
```

A thing that must become another ontological kind receives a new `RecordId` and an explicit relation. R0.2 forbids changing the kind in place.

## 4. PayloadDigest

The identity layer does not interpret semantic payloads. Each kind-specific layer must provide a strong digest in this form:

```text
sha256_<64 lowercase hexadecimal characters>
```

The canonicalization of a System, Question, Publication or other future payload is not defined here. R0.2 only requires that the admitted revision binds the exact `PayloadDigest` supplied by the responsible schema.

This prevents the identity layer from silently defining the future ontology.

## 5. Revision material and RevisionId

Every accepted revision is bound to this exact identity material:

```text
identitySchemaVersion
recordId
kind
generation
previousRevisionId
lifecycle
payloadDigest
```

The canonical byte serialization is UTF-8, LF-only, with a terminal LF and exactly this field order:

```text
identitySchemaVersion=<value>\n
recordId=<value>\n
kind=<value>\n
generation=<unsigned base-10 integer>\n
previousRevisionId=<revision id or ->\n
lifecycle=<value>\n
payloadDigest=<value>\n
```

`RevisionId` is:

```text
rev_sha256_<SHA-256(canonical revision material)>
```

The revision identifier is therefore content-addressed while the Record identifier is not.

Changing any revision-bound field produces a different `RevisionId` but does not by itself produce a different `RecordId`.

## 6. Birth

A candidate does not become a Record by appearing in a file or array.

Birth is the first accepted revision and MUST satisfy:

```text
generation = 0
previousRevisionId = null
RecordId has never been admitted
RecordKind is valid
RevisionId validates
lifecycle != tombstoned
```

Conceptually:

```text
provision RecordId
  -> validate global non-reuse
    -> validate kind
      -> validate revision material
        -> admit generation 0
          -> Record exists
```

Birth occurs at most once for one `RecordId`.

## 7. Lineage and successor admission

An accepted successor MUST satisfy all of the following:

```text
next.recordId == current.recordId
next.kind == current.kind
next.generation == current.generation + 1
next.previousRevisionId == current.revisionId
current.lifecycle != tombstoned
next.RevisionId validates
lifecycle transition is admitted
```

The authoritative lineage is therefore one predecessor-bound chain:

```text
revision 0
  -> revision 1
    -> revision 2
      -> ...
```

An overwrite, filesystem mtime, Git commit order, database row update or route change is not lineage authority.

## 8. Lifecycle

R0.2 freezes four identity-level lifecycle states:

```text
active
archived
withdrawn
tombstoned
```

`active`, `archived` and `withdrawn` may transition among one another through accepted revisions. Any of them may transition to `tombstoned`.

`tombstoned` is terminal. No successor revision may follow a tombstoned head.

Lifecycle is mutable state. It never changes `RecordId` or `RecordKind`.

## 9. Tombstone

A tombstone is not deletion of history. It is a final accepted revision with:

```text
lifecycle = tombstoned
```

The prior lineage remains reconstructable, the final `RevisionId` remains addressable and the `RecordId` remains permanently reserved.

Removing a file from a projection without an admitted tombstone MUST NOT be interpreted as ontological deletion.

## 10. Reconstruction

Persistent representations are evidence for reconstruction, not authority by themselves.

A reconstructed Record is admissible only if its lineage validates from birth to candidate head under the same identity rules.

The reconstruction algorithm MUST reject:

```text
invalid RecordId grammar
invalid kind grammar
invalid RevisionId
wrong generation sequence
wrong predecessor binding
kind mutation
RecordId mutation
successor after tombstone
incompatible candidate heads
```

It MUST NOT repair these states by silently selecting whichever representation has the newest timestamp or physical location.

## 11. Conflict

If reconstruction discovers two valid candidate heads that are not ancestrally ordered and no already-admitted authority record selects one of them, the lineage state is:

```text
CONFLICT
```

Conflict does not mint a synthetic head.

While conflicted:

```text
logical current-head resolution = unavailable
pinned historical resolution = allowed when independently valid
new normal successor admission = blocked
```

Resolution must be explicit and auditable. "Latest wins" is forbidden as an identity rule.

## 12. References

R0.2 defines two reference modes.

Logical reference:

```ts
{
  type: 'record',
  recordId
}
```

It follows the logical Record and resolves to the current admissible head.

Pinned reference:

```ts
{
  type: 'pinned-record',
  recordId,
  revisionId
}
```

It resolves exactly one accepted historical revision.

A claim, evidence assertion, migration witness or audit that depends on exact historical bytes SHOULD use a pinned reference. A general relation such as "this publication concerns this system" MAY use a logical reference.

## 13. Locators and aliases

A locator is an external address or storage handle. R0.2 does not freeze route grammar; R0.7 does.

The identity law is already normative:

```text
locator -> RecordId
```

never:

```text
locator == RecordId
```

Once a public locator has been bound to a `RecordId`, that historical binding MUST NOT later be silently reassigned to a different `RecordId`.

A moved canonical route becomes an alias or durable redirect to the same Record. Route migration does not mint a new Record.

## 14. Identity registry

The authoritative registry must be able to reconstruct at least:

```text
RecordId
RecordKind
birth RevisionId
current lineage state
current head RevisionId when available
tombstone RevisionId when terminal
historically bound locators
```

Registry presence is not semantic payload storage. It exists to prevent duplicate birth, kind mutation, identifier reuse and locator reassignment.

## 15. Revision order is not truth order

Generation expresses accepted temporal succession only.

```text
generation N+1 > generation N in lineage order
```

It does **not** imply:

```text
more true
better supported
more mature
more public
more important
```

Epistemic status belongs to the later ontology and Evidence/Claim contracts.

## 16. Representation independence

The following changes MUST NOT mint a new logical Record by themselves:

```text
React -> Astro
TS object -> Markdown / MDX
file A -> file B
one database -> another
one route -> another
one renderer -> another
one language representation -> another
one build artifact -> another
```

If the same identity is reconstructed under the same admitted lineage, it remains the same Record.

## 17. Graph independence

A relation may refer to Records but cannot rewrite them.

Creating:

```text
A --relates-to--> B
```

MUST NOT mutate `A.RecordId`, `B.RecordId`, either kind or either historical revision.

R0.3 will define semantic relationship types only after R0.2 is frozen.

## 18. Normative identity laws

The machine-readable companion `record-identity.v0.json` freezes RI-01 through RI-20. R0.2-PRE laws IG-01 through IG-15 remain research provenance; RI laws are the authority of this cut.

## 19. Explicit non-claims

R0.2 does not yet define:

- the first `RecordKind` registry;
- System, Question, Investigation, Experiment or Claim schemas;
- Evidence semantics;
- Architecture or Publication semantics;
- visibility, maturity or disclosure;
- public URL grammar;
- language representation identity;
- migration of legacy `Project` objects.

Those remain R0.3 through R0.8.
