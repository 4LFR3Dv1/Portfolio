# R0.5 — Publication & Architecture Contract

Status: **FROZEN**

Portfolio baseline: `main@95febe78f4572db229914010a7d83801d44bd839`

Precondition: `R0_4_COMPLETE=true`.

R0.5 freezes the first representation layer above the identity, knowledge and evidence substrates. It adds exactly two RecordKinds:

```text
representation.publication
representation.architecture
```

The governing separation is:

```text
knowledge / evidence
        ↓ interpreted by
representation
        ↓ rendered by
future public surface
```

A representation may explain, organize, cite and visualize the graph. It does not become the authority for the graph it represents.

## Publication

`representation.publication` is a durable editorial work with type, title, summary, opaque editorial body, logical `subjectRefs`, pinned historical `basisRefs` and optional logical `claimRefs`.

Publication types are:

```text
essay
research-note
experiment-report
system-note
technical-paper
```

Every logical subject and every machine-addressable Claim referenced by a Publication must have at least one pinned basis revision of the same RecordId. The split is intentional:

```text
subjectRefs
  -> what durable things the work is about

basisRefs
  -> which exact historical states the work interpreted
```

`body` is canonical editorial text, but R0.5 does not freeze Markdown, MDX, Astro, React or another rendering syntax.

Publication prose is narrative, not authority:

```text
Publication body != Claim
Publication basisRef != Evidence support
Publication claimRef != established Claim
```

A Publication may consult `evidence.artifact` or `evidence.binding` revisions through `basisRefs`. That does not create evidential support. Only R0.4 `evidence.binding` may encode `supports`, `contradicts` or `qualifies` semantics.

## Architecture

`representation.architecture` is a semantic representation of responsibilities, boundaries, components and relations.

Architecture types are:

```text
system
flow
protocol
boundary
conceptual
```

Architecture subjects are limited to:

```text
knowledge.system
knowledge.investigation
knowledge.experiment
```

Architecture may reference `knowledge.claim` Records as represented invariants, but every invariant Claim must have a pinned basis revision and remains governed by R0.3/R0.4 rather than by diagram text.

Architecture components use local IDs. A local component ID is not a RecordId and does not become an ontology entity by appearing in a representation. Relations connect those local IDs and are representational edges, not mutations of the canonical research graph.

If a component corresponds to an existing System, its `subjectRef` may bind that logical System, and the Architecture must include a pinned basis revision of the same RecordId.

## Architecture is not evidence

The following equivalences are forbidden:

```text
architecture relation == runtime observation
architecture boundary == evidence
invariantClaimRef == established invariant
```

Architecture can describe intended responsibility and boundaries. Evidence remains governed by R0.4.

## Anti-drift

Representations combine logical and pinned identity:

```text
RecordRef
  -> durable subject identity

PinnedRecordRef
  -> exact state interpreted by this representation revision
```

A later subject revision cannot retroactively rewrite an older Publication or Architecture. Incorporating later state requires a new representation revision under R0.2 lineage.

Changing prose, summary, basis, components, relations or boundaries revises only the representation Record. It does not rewrite any referenced Record identity or historical revision.

## Canonical payload profile

Both R0.5 kinds use canonical JSON:

- UTF-8;
- lexicographically sorted object keys;
- no insignificant whitespace;
- terminal LF;
- exact field sets;
- SHA-256 `PayloadDigest`;
- set-like reference arrays sorted deterministically after duplicate rejection.

Component, relation and boundary array order is preserved because it may carry narrative or flow meaning.

## Deferred boundary

R0.5 does not define:

```text
visibility
source availability
evidence visibility
maturity
disclosure policy
public/private/sanitized state
slug or route grammar
canonical URL
language identity or translation
legacy Project migration
final Publication templates
final Architecture UI
```

No R0.5 payload admits `visibility`, `maturity`, `slug`, `route`, `language`, `publishedAt` or `canonicalUrl`.

## Normative laws

`publication-architecture.v0.json` freezes PA-01 through PA-20. The executable contract validates exact payload fields, logical/pinned reference grammar, basis coverage, target-kind constraints, local architecture IDs, relation endpoints and canonical SHA-256 vectors.
