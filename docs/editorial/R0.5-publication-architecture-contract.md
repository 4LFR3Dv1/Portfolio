# R0.5 — Publication & Architecture Contract

Status: **NORMATIVE / IN PROGRESS**

Portfolio baseline: `main@95febe78f4572db229914010a7d83801d44bd839`

Precondition: `R0_4_COMPLETE=true`.

R0.5 defines the first representation layer on top of the frozen identity, knowledge and evidence substrates. It adds exactly two RecordKinds:

```text
representation.publication
representation.architecture
```

The governing boundary is simple:

```text
knowledge / evidence
        ↓ interpreted by
representation
        ↓ rendered by
future public surface
```

A representation may explain, organize, cite and visualize the graph. It does not become the authority for the graph it represents.

## 1. Publication

`representation.publication` is a durable editorial work.

```ts
{
  schemaVersion: 'representation.publication/v0'
  publicationType:
    | 'essay'
    | 'research-note'
    | 'experiment-report'
    | 'system-note'
    | 'technical-paper'
  title: string
  summary: string
  body: string
  subjectRefs: RecordRef[]
  basisRefs: PinnedRecordRef[]
  claimRefs: RecordRef[]
}
```

`body` is canonical editorial text but its rendering syntax is intentionally opaque to R0.5. Markdown, MDX, Astro, React or any other renderer remains an implementation concern for R1.

A Publication MUST have at least one logical subject and at least one pinned historical basis. Every logical subject and every referenced Claim must have a pinned basis revision of the same RecordId.

This gives Publication two simultaneous identities of reference:

```text
subjectRefs
  -> what durable things the work is about

basisRefs
  -> which exact historical states the work actually interpreted
```

A 2026 publication about a System therefore remains about that System while still being mechanically bound to the exact System revision it observed at publication revision time.

## 2. Publication is not a truth source

Publication prose may contain interpretation, argument and explanation. It MUST NOT silently create canonical facts.

Machine-addressable propositions remain `knowledge.claim` Records. Evidential support, contradiction and qualification remain `evidence.binding` Records.

Therefore:

```text
Publication body != Claim
Publication basisRef != Evidence support
Publication claimRef != established Claim
```

A raw `evidence.artifact` may appear in Publication `basisRefs` as material consulted. That reference alone does not mean the artifact supports any Claim. Only R0.4 `evidence.binding` can encode `supports`, `contradicts` or `qualifies` semantics.

This preserves EC-02, EC-03 and EC-04 through the presentation layer.

## 3. Architecture

`representation.architecture` is a semantic representation of responsibilities, boundaries, components and relations.

```ts
{
  schemaVersion: 'representation.architecture/v0'
  architectureType:
    | 'system'
    | 'flow'
    | 'protocol'
    | 'boundary'
    | 'conceptual'
  title: string
  summary: string
  subjectRefs: RecordRef[]
  basisRefs: PinnedRecordRef[]
  components: ArchitectureComponent[]
  relations: ArchitectureRelation[]
  boundaries: string[]
  invariantClaimRefs: RecordRef[]
}
```

R0.5 Architecture subjects may resolve only to:

```text
knowledge.system
knowledge.investigation
knowledge.experiment
```

An Architecture can reference `knowledge.claim` Records as represented invariants, but those Claims remain external Records and require pinned basis revisions.

## 4. Local architecture components

Architecture component IDs are local representation identifiers:

```text
proposal
authority
runtime
reconciliation
```

They are not `RecordId` values and do not become independent ontology entities merely because they appear in a diagram.

```ts
{
  id: string
  label: string
  responsibility: string
  subjectRef: RecordRef | null
}
```

When a component corresponds to an existing System Record, `subjectRef` may bind that logical System. The Architecture `basisRefs` must then contain at least one pinned revision of that same RecordId.

Architecture relations connect local component IDs:

```ts
{
  from: string
  to: string
  label: string
}
```

These are representational edges. They MUST NOT mutate or replace the canonical research graph established by R0.3.

## 5. Architecture is not evidence

An Architecture may describe what a boundary is intended to do. It does not prove the runtime behaves that way.

```text
architecture relation
    != runtime observation

architecture boundary text
    != evidence

invariantClaimRef
    != established invariant
```

If an invariant Claim has Evidence, R0.4 remains the authority for the binding and derived evidential disposition.

This is the executable form of EC-10: Architecture is representation.

## 6. Anti-drift through logical + pinned references

Representations use logical refs for durable subject identity and pinned refs for historical interpretation.

```text
RecordRef
  -> same logical subject through time

PinnedRecordRef
  -> exact state interpreted by this representation revision
```

A later subject revision does not retroactively rewrite an older Publication or Architecture. Updating the representation to incorporate that later state produces a new representation revision under R0.2 lineage.

## 7. Representation revision does not rewrite subjects

Changing any of the following revises only the representation Record:

```text
Publication prose
Publication summary
Publication basis
Architecture components
Architecture relations
Architecture boundaries
Architecture basis
```

No such change mutates the identity or history of referenced System, Question, Investigation, Experiment, Claim or Evidence Records.

## 8. Canonical payloads

Both R0.5 kinds use the same canonical JSON profile already established for semantic payloads:

- UTF-8;
- lexicographically sorted object keys;
- no insignificant whitespace;
- terminal LF;
- exact field sets;
- SHA-256 `PayloadDigest`;
- set-like reference arrays sorted deterministically after duplicate rejection.

Component order, relation order and boundary order are preserved because they may carry narrative or flow meaning.

R0.5 includes one independent SHA-256 payload vector for each new RecordKind.

## 9. Exact deferred boundary

R0.5 explicitly does not define:

```text
visibility
source availability
evidence visibility
maturity
disclosure policy
public/private/sanitized state
slug or route grammar
canonical URL
language identity or translation
legacy Project migration
final publication templates
final Architecture UI
```

Those belong to R0.6 through R1.

No field named `visibility`, `maturity`, `slug`, `route`, `language`, `publishedAt` or `canonicalUrl` is admitted by an R0.5 payload.

## 10. Normative laws

The machine-readable companion `publication-architecture.v0.json` freezes PA-01 through PA-20.

The core rules are:

```text
Publication != source of truth
Architecture != evidence
logical subject identity != historical basis
subject refs require pinned basis
Claim refs require pinned basis
Evidence basis != Evidence binding
Architecture components are local
Architecture edges are representational
representation revision does not rewrite subjects
later visibility/route/language semantics remain absent
```
