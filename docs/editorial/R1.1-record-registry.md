# R1.1 — Record Registry

Status: **MATERIALIZED / AWAITING CI WITNESS**

Baseline: `main@650ca686854110ec817e47f1658bf37e6d1a2daf`

Preconditions:

```text
R0_EFFECTIVE_COMPLETE=true
R1_PRE_COMPLETE=true
R1_0_COMPLETE=true
```

R1.1 is the first cut in which grounded durable subjects become born Records.

R1-PRE reconstructed the connected GitHub corpus and identified 28 durable System subjects, but deliberately left `birthAuthorized=false` for every subject. Grounding was evidence for an admission decision; it was not itself authority to mint identity.

R1.1 now performs that explicit admission.

## 1. Admission boundary

The R1.1 birth batch contains exactly:

```text
15 frontier-grounded System subjects
13 historical-grounded System subjects
--------------------------------------
28 knowledge.system Births
```

No repository becomes a Record merely because it exists.

No non-System treatment from R1-PRE becomes a Record in this cut.

No Question, Investigation, Experiment, Claim, Evidence, Publication, Architecture, governance decision, route binding or language realization is born by implication.

The distinction is:

```text
R1-PRE
  identifies durable subjects

R1.1
  explicitly admits System identity
```

not:

```text
repository discovered
  -> Record automatically minted
```

## 2. Generation-zero Birth

Each admitted System has exactly one generation-zero revision:

```text
RecordId             opaque stable identity
RecordKind           knowledge.system
generation           0
previousRevisionId   null
lifecycle            active
payloadDigest        SHA-256 of canonical R0.3 payload bytes
RevisionId           SHA-256 of canonical R0.2 revision material
```

Every payload is an exact R0.3 `knowledge.system/v0` payload.

R1.1 intentionally uses conservative generation-zero semantics:

```text
name     grounded subject label
summary  admission-safe System description
thesis   null
```

This avoids converting repository READMEs, old marketing copy or grounding notes into unreviewed System claims at Birth.

A later accepted revision may enrich the semantic payload without changing `RecordId`.

## 3. Grounding class is not Maturity

The registry retains `frontier-system` and `historical-system` as **admission provenance** because those classes explain how R1-PRE partitioned the corpus.

They are not R0.6 maturity values.

Therefore:

```text
subjectClass=frontier-system
!=
maturity=production
```

and:

```text
subjectClass=historical-system
!=
lifecycle=archived
```

All generation-zero Records are born `active`. Maturity and disclosure remain separate governance decisions.

```text

XS Wallet / Domini         rec_724d518ee338e32eb06e79077ad01f3d
Transactional Support Bot  rec_c5a75fd5ecae0565aaa0c96f0ad53227
```

This preserves the migration identity already reserved for those subjects.

The `XS Wallet / Domini` name remains deliberately conservative because R1-PRE left the final public naming question unresolved. That naming question does not block Birth: a future semantic revision can change the name while preserving the same logical Record identity.

## 5. New opaque identities

The other 23 Systems receive new opaque 128-bit RecordIds.

The IDs are not derived from:

```text
repository name
System title
slug
URL
owner
Git commit
payload digest
```

This preserves the R0.2 rule that mutable or presentational data cannot constitute logical identity.

## 6. The retired Agentic reservation remains impossible to reuse

R0-A1 retired before Birth:

```text
rec_d5549271c541d17165c0ad8512dcdcc1
```

R1.1 places that identifier in the unavailable identity pool as `retired-pre-birth`.

It does not become a tombstoned Record because it was never born.

The registry rejects any attempted Birth using that ID.

## 7. Held R0.8 reservations

R0.8 also reserved identities for legacy Publications and Architectures.

R1.1 does not manufacture those representations simply because their identifiers exist. They remain held and unavailable for reuse until an explicit representation admission cut supplies valid payloads and relationships.

Held reservations:

```text
3 representation.publication identities
5 representation.architecture identities
```

A held reservation is not a Record.

## 8. Registry reconstruction

`src/editorial/record-registry.ts` establishes the framework-independent registry core.

For every Record it validates:

```text
RecordId grammar
RecordKind grammar
payload schema
canonical payload digest
RevisionId digest
exactly one Birth
predecessor continuity
generation continuity
kind continuity
lifecycle transitions
lineage connectivity
current-head uniqueness
```

The registry exposes reconstructed current heads only after these checks pass.

A corrupted payload, invalid predecessor or competing current heads does not receive a repaired synthetic state.

## 9. Conflict semantics

Two valid successors of the same accepted revision remain two competing heads:

```text
             revision 0
              /      \
       revision 1A  revision 1B
              \      /
               CONFLICT
```

R1.1 does not choose:

```text
latest timestamp
last file order
highest lexical RevisionId
first loaded revision
```

There is no latest-wins reconstruction.

## 10. Extensibility without silent ontology changes

The Record Registry core accepts explicit payload codecs.

R1.1 supplies codecs for the already-frozen R0.3 Knowledge kinds. Future R1 cuts may supply codecs for Evidence, Representation or Governance Records when those records are explicitly admitted, without changing the meaning of Record identity or allowing an unknown kind to bypass validation.

Unsupported kinds fail closed.

## 11. Birth does not mean publication

A born Record is not automatically public.

R1.1 does not create or infer:

```text
disclosure decisions
maturity decisions
canonical routes
language realizations
projection eligibility
HTML pages
search entries
RSS entries
```

Those remain later R1 responsibilities.

Therefore a private, historical or not-yet-disclosed System may possess durable Record identity without appearing anywhere on the public site.

## 12. Public/runtime boundary

R1.1 does not install Astro and does not alter the deployed React/Vite SPA.

```text
framework cutover    false
public UI changed    false
runtime semantics    false
```

The registry is build-time editorial substrate only.
