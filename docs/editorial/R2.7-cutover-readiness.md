# R2.7 — Cutover Readiness

Status: **MATERIALIZED / AWAITING READ-ONLY PRODUCTION WITNESS**

Baseline: `main@1479b5ce092655c770bc24dee8c94fc825db931e`

R2.7 does not publish the editorial runtime to `renan.snelabs.space`. It determines whether the already-accepted R2.6 deployment can be promoted by a bounded, reversible control-plane transaction without changing the runtime that was physically proved.

## 1. Regime

R2.6 proved:

```text
commissioned R2.5 runtime
        ↓
isolated Railway deployment
        ↓
real Internet / TLS / hosting
        ↓
semantic differential = 0
```

R2.7 asks a different question:

```text
accepted R2.6 target
        +
exact current production baseline
        +
bounded domain handoff
        +
exact rollback baseline
        ↓
is cutover executable without inventing anything at cutover time?
```

Readiness is not authorization.

```text
CUTOVER_READY=true
        !=
CUTOVER_AUTHORIZED=true
        !=
CUTOVER_ENACTED=true
```

## 2. Accepted target

The target is not rebuilt for R2.7.

The accepted target remains the R2.6 Railway deployment:

```text
deployment  52b5b9ef-a80a-4ee2-8c54-20aa25975553
origin      https://r2-6-preview-production.up.railway.app
runtime     R2.5 commissioned runtime
```

A fresh external witness must prove that this target still has zero semantic differences before readiness can be sealed.

R2.7 forbids replacing the accepted deployment with a newly interpreted hosting implementation.

## 3. Current production becomes an observed rollback baseline

R2.6 excluded the production origin entirely. R2.7 may observe it, but only read-only.

The readiness witness records:

- current public DNS answers for `renan.snelabs.space`;
- current nameservers and SOA for `snelabs.space`;
- current production HTTP root fingerprint;
- current production `robots.txt` and `sitemap.xml` status/fingerprint;
- transport/provider headers that help identify the incumbent path;
- the still-authoritative root repository deployment contract.

No DNS, domain, Vercel, Railway custom-domain or production repository write is permitted in R2.7.

## 4. Cutover transaction

R2.7 freezes the intended R2.8 transaction as a domain handoff to the exact accepted R2.6 service.

```text
accepted Railway service remains unchanged
        ↓
attach renan.snelabs.space to that service
        ↓
provider returns required domain/DNS binding
        ↓
verify target binding before traffic move
        ↓
mutate only renan.snelabs.space DNS
        ↓
traffic moves to already-proved runtime
```

The following are explicitly outside the R2.8 write set unless a later amendment is accepted:

```text
snelabs.space apex
*.snelabs.space wildcard
www.renan.snelabs.space
root package build script
root vercel.json
editorial semantic runtime
accepted R2.6 deployment contents
```

The current React/Vite deployment is not destroyed before acceptance. It remains the rollback runtime.

## 5. Why the old production runtime remains alive

Cutover and retirement are separate events.

```text
old production runtime preserved
        +
new domain handoff enacted
        ↓
R2.9 physical acceptance
        ↓
only then may retirement be considered
```

A failed R2.8/R2.9 campaign must not require reconstructing the old site from source before rollback.

## 6. Rollback contract

Before cutover, R2.7 must freeze the exact current DNS answer set and production fingerprint.

Rollback is defined as:

```text
failure after traffic move
        ↓
restore exact pre-cutover DNS state
        ↓
verify old production HTTP fingerprint is reachable again
        ↓
only then remove/alter failed target bindings if needed
```

Rollback therefore precedes destructive cleanup.

## 7. Physical readiness witness

`.github/workflows/editorial-cutover-readiness.yml` is a read-only physical campaign.

It performs:

```text
locked editorial build
→ R2.5 commissioning re-proof
→ R2.6 fresh Internet/TLS equivalence witness
→ public DNS observation of current production
→ current production HTTP fingerprint
→ repository production-contract verification
→ durable R2.7 readiness witness artifact
```

The workflow must report `production_mutation_count=0`.

## 8. Acceptance

R2.7 can be sealed only if all of the following are physically true:

```text
R2_6_COMPLETE=true
ACCEPTED_TARGET_STILL_EQUIVALENT=true
CURRENT_PRODUCTION_DNS_CAPTURED=true
CURRENT_PRODUCTION_HTTP_CAPTURED=true
ROLLBACK_BASELINE_CAPTURED=true
CUTOVER_WRITE_SET_BOUNDED=true
PRODUCTION_MUTATION_COUNT=0
```

Then, and only then:

```text
R2_7_COMPLETE=true
CUTOVER_READY=true
CUTOVER_AUTHORIZED=false
```

R2.7 itself may not authorize or enact the public cutover.
