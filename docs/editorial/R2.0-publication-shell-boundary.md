R2 begins physical publication work, but R2.0 deliberately freezes the shell boundary before introducing a framework dependency or changing deployment.

The implementation family remains the one selected by R1.0:

```text

```

At this cut, `astro` is **not yet installed**. That physical package/runtime materialization belongs to R2.1. R2.0 first makes the input/output authority of that shell executable so the renderer cannot become a new semantic source while the framework is introduced.

## 1. Authority direction

The shell consumes only accepted R1 outputs:

```text
R1.7 Distribution Bundle
        +
R1.8 Legacy Compatibility
        +
R1.9 Foundation Acceptance
        ↓
Publication Shell Plan
        ↓
future Astro renderer
```

The shell MUST NOT discover pages by crawling:

```text
Record Registry
Evidence
Governance
GitHub
filesystem names
legacy React components
```

Those may remain upstream implementation/provenance inputs, but they are not renderer-facing page discovery authority.

## 2. Canonical static pages

Every canonical page planned by R2.0 must already exist in the accepted R1.7 distribution bundle.

```text

        ↓ exact projection

```

There is no manual Astro page registry and no `slug -> page` inference at the shell boundary.

Metadata and hreflang remain page-level data from the same Distribution Bundle rather than separate hand-maintained registries.

No artifact is physically deployed by R2.0.

## 6. Unknown paths

The publication shell boundary freezes:

```text
unknown path -> 404
```

This is the target static-shell behavior already accepted by R1.8/R1.9. It is not yet enacted on the currently deployed SPA.

## 7. Renderer non-authority

The future renderer may format admitted data, but it may not:

```text
mint a Record
select a different Record head
change disclosure
read private Evidence to enrich a page
infer a missing language
perform runtime sanitization
repair semantic conflicts
rewrite legacy meaning
```

The renderer receives a publication plan and bounded DTOs, not institutional authority.

## 8. Why Astro is not installed in this cut

R1.9 proved that foundation readiness is not cutover readiness. R2.0 applies the same separation to the framework boundary.

Installing Astro and creating renderable pages changes the physical build graph. Before doing that, the repository now has an executable contract for exactly what the framework is allowed to consume and emit.

Therefore:

```text
R2.0  shell authority + plan boundary
R2.1  Astro dependency + physical renderer materialization
```

This keeps package/runtime changes out of the same cut that defines their authority constraints.

## 9. Deployment boundary

So the deployed React/Vite site remains unchanged.
