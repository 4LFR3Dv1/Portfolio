# R0.3 — Knowledge Ontology

Status: **FROZEN**

Portfolio baseline: `main@bfe7c6f48ece7d408e07e29a67c74ffec87e0578`

Precondition: `R0_2_COMPLETE=true`.

R0.3 defines the first semantic `RecordKind` registry on top of the frozen R0.2 identity substrate. It introduces only five knowledge kinds:

```text
knowledge.system
knowledge.question
knowledge.investigation
knowledge.experiment
knowledge.claim
```

R0.3 does not yet define Evidence, Publication, Architecture, visibility, maturity, disclosure, route grammar or language identity. Those remain later cuts.

## 1. Ontological boundary

A Record kind answers **what kind of thing this Record is**, not how it is rendered or where it is stored.

```text
RecordId
  -> RecordKind
      -> kind-specific semantic payload
          -> canonical payload bytes
              -> PayloadDigest
                  -> R0.2 RevisionId
```

R0.2 owns logical identity and revision lineage. R0.3 owns the semantic payload schemas for the first five kinds.

## 2. `knowledge.system`

A System is a durable object of construction, operation or inquiry. It is not a publication, maturity label, repository or route.

Canonical payload:

```ts
{
  schemaVersion: 'knowledge.system/v0'
  name: string
  summary: string
  thesis: string | null
}
```

`name`, `summary` and an optional `thesis` describe the System. R0.3 deliberately does not add maturity, source visibility, deployment state or publication links.

## 3. `knowledge.question`

A Question is a durable epistemic object. It may remain unresolved indefinitely.

Canonical payload:

```ts
{
  schemaVersion: 'knowledge.question/v0'
  prompt: string
  state: 'open' | 'investigating' | 'partially-answered' | 'answered' | 'superseded'
  aboutSystemRefs: RecordRef[]
  parentQuestionRef: RecordRef | null
}
```

`aboutSystemRefs` is set-like and resolves only `knowledge.system` Records. `parentQuestionRef`, when present, resolves only another `knowledge.question` and must not self-reference.

Question state expresses the current admitted editorial/research state. It does not manufacture evidence or certainty.

## 4. `knowledge.investigation`

An Investigation is bounded work undertaken to address one or more Questions.

```ts
{
  schemaVersion: 'knowledge.investigation/v0'
  title: string
  scope: string
  state: 'planned' | 'active' | 'paused' | 'completed' | 'abandoned'
  questionRefs: RecordRef[]
}
```

At least one Question is required. The Investigation does not own the Question and does not rewrite it. Inverse navigation is derived by graph query rather than duplicated into the Question payload.

## 5. `knowledge.experiment`

An Experiment is a bounded procedure conducted inside one or more Investigations.

```ts
{
  schemaVersion: 'knowledge.experiment/v0'
  title: string
  protocol: string
  declaredOutcome: 'not-run' | 'pass' | 'fail' | 'inconclusive'
  investigationRefs: RecordRef[]
}
```

At least one Investigation is required.

`declaredOutcome` is intentionally named as such: it is the admitted outcome asserted by the Experiment payload. It is not operational evidence and is not self-validating. R0.4 defines what evidence may support an experimental result.

## 6. `knowledge.claim`

A Claim is an explicitly scoped proposition.

```ts
{
  schemaVersion: 'knowledge.claim/v0'
  statement: string
  scope: string
  aboutRefs: RecordRef[]
}
```

`aboutRefs` may resolve only System, Question, Investigation or Experiment Records in R0.3.

R0.3 intentionally defines **no epistemic status** such as supported, established or refuted. A Claim does not become true because it exists, because it is newer, or because another Record links to it. Support/refutation semantics belong to R0.4.

## 7. Directional graph rule

R0.3 stores only the canonical forward relationships necessary to express the research chain:

```text
System
  ^
  | about
Question
  ^
  | addressed-by
Investigation
  ^
  | contains
Experiment

Claim --about--> System | Question | Investigation | Experiment
```

Reverse lists are projections. For example, a System payload does not store every Question that references it. This avoids dual authorities and relation drift.

Adding a relationship revises the source Record payload under R0.2 lineage rules; it does not rewrite the target Record or any historical revision.

## 8. Reference semantics

Knowledge relationships use logical `RecordRef` only.

```text
{ type: 'record', recordId }
```

Pinned historical references remain available in R0.2 but are not embedded in R0.3 knowledge payloads. R0.4 may require pinned references where evidence/audit semantics depend on exact historical state.

Every R0.3 graph reference must resolve and must satisfy its target-kind constraint.

## 9. Canonical semantic payload

R0.3 freezes one implementation-neutral canonical JSON profile:

- UTF-8;
- JSON values only;
- object keys sorted lexicographically;
- array order preserved unless the schema declares the array set-like;
- set-like RecordRef arrays sorted by `recordId` after duplicate rejection;
- no insignificant whitespace;
- one terminal LF;
- no implicit fields;
- no `undefined`, NaN or Infinity;
- strings are preserved exactly; Unicode normalization is not performed by this cut.

`PayloadDigest` is:

```text
sha256_<SHA-256(canonical payload bytes)>
```

The digest binds semantic payload bytes but does not become logical Record identity.

## 10. Exact schemas only

Each kind accepts only its frozen field set. Unknown fields fail validation rather than silently becoming part of the ontology.

This is particularly important for future cuts: R0.4 cannot smuggle Evidence into a Claim payload, R0.6 cannot silently add maturity to System, and R0.7 cannot turn routes or language representations into System identity. Those changes require their owning contracts.

## 11. Explicit deferred semantics

R0.3 does not define:

```text
Evidence records or evidence relations
Claim support / refutation / epistemic rank
Architecture records
Publication records
visibility / source availability / disclosure
maturity
public URL grammar
language representation identity
legacy Project migration
```

No field named `evidence`, `evidenceRefs`, `supportRefs`, `maturity`, `visibility`, `slug`, `route`, `language` or `publicationRefs` is part of any R0.3 payload.

## 12. Normative knowledge laws

The machine-readable companion `knowledge-ontology.v0.json` freezes KO-01 through KO-18.

The critical rules are:

- exactly five initial knowledge kinds;
- kind-specific exact payload schemas;
- Systems remain independent of publications and maturity;
- Questions may remain unresolved;
- Investigations require Questions;
- Experiments require Investigations;
- declared Experiment outcome is not evidence;
- Claims are propositions, not self-validating conclusions;
- Evidence semantics remain absent until R0.4;
- graph references resolve and obey target kinds;
- reverse relationships are derived, not duplicated;
- semantic payload digests are canonical and deterministic;
- knowledge relations do not rewrite target identity/history.
