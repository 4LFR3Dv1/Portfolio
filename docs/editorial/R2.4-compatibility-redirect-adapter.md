# R2.4 — Compatibility Redirect Adapter

Status: **MATERIALIZED / AWAITING DUAL CI WITNESS**

Baseline: `main@13b53a9874185eb63667e82f5504865693b36e27`

R2.4 materializes the four R1.8 redirect-ready legacy paths without activating them in production.

The central constraint is physical: the historical language source is browser `localStorage`, while an HTTP server cannot read browser `localStorage` on the incoming request. Therefore a truthful 302 implementation cannot pretend that server-side language negotiation happens directly.

R2.4 uses a two-stage compatibility adapter.

```text
legacy route request
      ↓
static compatibility handshake
      ↓
read localStorage["portfolio-language"]
      ↓
explicit {from, lang} request
      ↓
bounded HTTP redirect adapter
      ↓
302 Location: distributed canonical successor
```

## 1. Redirect-ready paths

Exactly four legacy paths are admitted:

```text
/
/work/vira
/work/xs-wallet
/work/sne-os
```

Their successors continue to come only from the R1.8 compatibility contract and R2.0 shell plan.

```text
/                  → /en | /pt-br
/work/vira         → /en/systems/vira | /pt-br/systems/vira
/work/xs-wallet    → /en/systems/xs-wallet | /pt-br/systems/xs-wallet
/work/sne-os       → /en/systems/sne-os | /pt-br/systems/sne-os
```

R2.4 does not infer any successor and refuses to materialize if any of the eight target pages is absent from the accepted R1.7 distribution.

## 2. Client language handshake

The compatibility handshake preserves the historical client-state contract:

```text
localStorage["portfolio-language"]
  pt      → pt
  en      → en
  missing → en
  other   → en
```

The handshake then requests:

```text
/_compat/redirect?from=<legacy-path>&lang=<en|pt>
```

No `navigator.language`, `Accept-Language`, geolocation or cross-language fallback participates.

The server adapter requires the language hint explicitly. A request without `lang` fails with HTTP 400 instead of inferring language from request headers.

## 3. HTTP redirect contract

For an admitted source path and explicit valid language whose successor is still distributed:

```text
HTTP 302
Location: <exact admitted canonical successor>
Cache-Control: no-store
```

The 302 is deliberately temporary because the historical URL is language-ambiguous: the exact target depends on the client state.

## 4. Fail-closed successor validation

The adapter rechecks the target against the distributed canonical-path set at request resolution time.

If a target that existed during admission is no longer distributable:

```text
known legacy path
+ valid explicit language
+ successor absent from distributed state
        ↓
HTTP 503
NO Location header
```

It never redirects to another language, another System or a guessed route.

Unknown or preserved legacy paths are outside this adapter and resolve as 404 at the adapter boundary. They remain responsibilities of R2.3 or the future general 404 runtime.

## 5. Static handshake pages

The isolated Astro shell now physically emits four non-canonical handshake pages for the redirect-ready legacy paths.

These pages:

```text
robots = noindex,follow
canonical = absent
hreflang = absent
```

and remain absent from sitemap, RSS and search.

They are transport compatibility surfaces, not editorial documents.

## 6. Physical HTTP witness

`editorial-shell/scripts/verify-redirect-adapter.mjs` starts an ephemeral local HTTP server over the exact TypeScript adapter and accepted renderer input, then performs real HTTP requests with redirect following disabled.

The witness requires:

- EN VIRA → 302 `/en/systems/vira`;
- PT VIRA → 302 `/pt-br/systems/vira`;
- missing explicit language + Portuguese `Accept-Language` → 400, proving no header inference;
- preserved Agentic route → 404 at the redirect adapter boundary;
- removal of PT-BR VIRA from the distributed target set → 503 with no `Location` header.

This proves HTTP behavior without mutating production routing.

## 7. Deployment boundary

R2.4 does not activate the adapter on `renan.snelabs.space`.

```text
root build                  vite build
vercel.json                 unchanged
production React SPA        authoritative
Astro static shell          isolated build only
HTTP redirect adapter       witnessed locally only
production redirects        false
```

No Vercel route, serverless function, middleware or root build cutover is introduced in this cut.

## 8. Acceptance

R2.4 closes only after root Verify and Editorial Shell Build pass against the same materialized state and prove:

- exactly four redirect entries;
- exactly eight admitted distributed targets;
- four static client-state handshake pages;
- `portfolio-language` as the sole language source;
- explicit EN/PT mapping and English default;
- exact HTTP 302 + `Location` behavior;
- zero `Accept-Language` or navigator inference;
- fail-closed 503 with no Location on successor loss;
- preserved legacy routes excluded from redirect handling;
- redirect handshake pages excluded from sitemap/RSS/search;
- production deploy remains unchanged.
