# R1.8 — Legacy Compatibility

Status: **MATERIALIZED / AWAITING CI WITNESS**

Baseline: `main@67cf446ca1482ed7b8fae77e8aa5a7b8182fe10a`

Preconditions:

```text
R0_EFFECTIVE_COMPLETE=true
R1_6_COMPLETE=true
R1_7_COMPLETE=true
```

R1.8 materializes the compatibility boundary between the currently deployed React/Vite Portfolio and the new editorial identity/distribution world without performing the public cutover.

The cut is deliberately asymmetric:

```text
legacy public locator
        ↓
compatibility decision
        ├── safe distributed successor exists
        │       → language-negotiated redirect plan
        │
        └── successor is absent, unsafe or semantically ambiguous
                → preserve frozen legacy representation
```

It never performs:

```text
legacy URL → nearest modern concept
legacy URL → undistributed future route
legacy locale ambiguity → guessed translation
unknown URL → home
```

## 1. Physical deployed legacy state is explicit

The deployed application still has eight frozen public routes:

```text
/
/architecture
/work/vira
/work/xs-wallet
/work/agentic-systems
/work/transactional-support-bot
/work/sne-os
/work/verify-systems
```

Its client router still falls unknown extensionless paths back to the landing view, Vercel still rewrites extensionless requests to `/index.html`, and language is still stored under:

```text
portfolio-language
```

with legacy values:

```text
en
pt
```

and English as the default.

R1.8 grounds this behavior because compatibility cannot preserve what it does not describe.

## 2. The compatibility registry is a finite legacy exception set

R1.7 prohibited a second manual registry of editorial pages. R1.8 does not weaken that rule.

Its eight-entry table is not a new page authority. It is a finite compatibility registry whose source is exactly the R0.0 frozen public route set plus the R0.8 migration plan and R0-A1 amendment.

A compatibility entry may point to a successor only when that successor is already present in the R1.7 authorized distribution bundle.

Therefore:

```text
compatibility table
    may preserve old locators
    may choose among already-authorized successors
    MUST NOT create a new canonical page
```

## 3. Four legacy paths are redirect-ready

The following paths have complete, already-distributed EN and PT-BR successors:

```text
/
/work/vira
/work/xs-wallet
/work/sne-os
```

Their future compatibility behavior is language-negotiated using the same client state that controlled the legacy page:

```text
portfolio-language=en
    → EN successor

portfolio-language=pt
    → PT-BR successor

missing state
    → EN successor
```

Examples:

```text
/work/vira + en
    → /en/systems/vira

/work/vira + pt
    → /pt-br/systems/vira
```

The compatibility redirect is modeled as HTTP `302` because one legacy locator does not possess one language-independent permanent canonical successor. The canonical identity remains on the locale-specific destination.

R1.8 does not enact these redirects yet.

## 4. Four legacy representations must remain renderable

The following paths cannot safely redirect yet:

```text
/architecture
/work/agentic-systems
/work/transactional-support-bot
/work/verify-systems
```

Their reasons are different and must remain explicit.

### `/architecture`

The legacy Architecture Explorer is preserved because the planned `representation.architecture` Records have not been Born and distributed. No architecture successor is manufactured from service naming alone.

### `/work/agentic-systems`

R0-A1 already established that this historical representation has no canonical System successor. Its locator must never be rebound to Foundry, Factory, AgentHub or another modern System.

```text
preserve historical representation
!=
assert durable System continuity
```

### `/work/transactional-support-bot`

Canonical System routes exist, but the current R1.6/R1.7 distribution deliberately omits semantic documents because disclosure is `sanitized` and no independently admitted disclosure-safe content authority exists.

Therefore redirecting the old case study would be a regression: it would replace a valid frozen sanitized public representation with an unavailable semantic page.

The old representation remains until safe content exists.

### `/work/verify-systems`

The future Publication identity remains reserved but unborn. The existing case-study representation and public PDF survive as legacy material; R1.8 does not pretend that `/en/research/verify-systems` is already a distributed Publication page.

## 5. Language compatibility preserves old state without creating new authority

R1.8 maps only the existing legacy client values:

```text
en → en
pt → pt-BR
```

It does not infer from `Accept-Language`, geography, browser locale or content availability.

No PT-BR successor may fall back to EN through the compatibility layer.

The compatibility resolver is pure: a caller supplies the observed legacy client state. Reading browser storage belongs to the eventual cutover adapter, not to the identity core.

## 6. Unknown paths change meaning only at cutover

The current SPA still behaves as:

```text
unknown path
    → landing
```

R0.7 already established that this cannot remain the target identity semantics.

R1.8 therefore freezes the future compatibility result as:

```text
unknown path
    → unresolved
```

The current deployed router is not modified by this cut. The new behavior becomes physical only when the publication runtime is cut over.

## 7. Legacy sitemap remains deployed

R1.7 already materialized the future editorial sitemap from authorized distribution state.

R1.8 does not replace `public/sitemap.xml` yet because the current deployed runtime still serves the legacy URL world.

This keeps deployment coherent:

```text
legacy runtime active
    → legacy sitemap active

future editorial runtime active
    → generated editorial sitemap active
```

There is no interval in which the deployed sitemap advertises pages the deployed runtime cannot serve.

## 8. Compatibility is not canonical identity

A compatibility redirect does not create a RouteBinding.
A preserved legacy representation does not become a Record.
A legacy language hint does not become a LanguageBinding.
A legacy URL does not become the canonical URL merely because it remains durable.

The compatibility boundary exists only to preserve historical public semantics while the new canonical world takes over.

## 9. Deployment remains unchanged

R1.8 does not enact:

```text
compatibility redirects
legacy fallback renderer
Astro cutover
static HTML rendering
Vercel configuration changes
legacy sitemap replacement
public UI changes
```

The React/Vite application remains the deployed public runtime.
